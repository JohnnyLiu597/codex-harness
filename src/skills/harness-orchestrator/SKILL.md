# Harness Orchestrator Skill v2.0

> Architecture: coordinator/worker pattern with isolated context and compact synthesis

## Use this skill when
- Task has 3+ separable sub-goals (candidate for parallel execution)
- Acting as coordinator that spawns workers
- Running sequential multi-phase workflows with quality gates
- Sub-goals require different tool sets or model tiers
- Using `/plan`, `/coordinate`, `/orchestrate`, or `/ultrawork`

## Do not use this skill when
- Task is linear with no parallelism (< 3 steps, tightly coupled)
- Task is short (< 20 total tool calls estimated)
- You are a worker sub-agent (not coordinator)

## Instructions

### Phase 0: Task Decomposition

```markdown
## Task Decomposition Analysis
Original task: {task}

Sub-goal analysis:
| ID | Sub-goal | Dependencies | Est. calls | Can parallelize? |
|----|----------|-------------|------------|-----------------|
| A  | {goal}   | none        | N          | YES             |
| B  | {goal}   | none        | N          | YES             |
| C  | {goal}   | A           | N          | NO (needs A)    |

Execution plan:
  Batch 1 (parallel): A, B
  After batch 1: C (requires A output)

Total estimated tool calls: N
Model routing:
  A 鈫?fast-model (routine task)
  B 鈫?fast-model (routine task)
  C 鈫?reasoning-model (requires synthesis/reasoning)
```

### Worker Spawn Pattern

Workers are autonomous sub-agents with minimal context and explicit output contracts.

```markdown
## Sub-agent Brief: {agent_id}
> Generated by: harness-orchestrator
> Parent coordinator: {coordinator_id}
> Task type: worker

### Goal (single, precise, measurable)
{one-sentence goal 鈥?no ambiguity, no compound tasks}

### Context Package (minimal 鈥?no context bleed)
{list only the facts this worker needs}
{test: "Would the worker fail without this fact?" 鈥?if no, exclude}

### Tool Allowlist
{list only needed tools 鈥?workers should not get full tool set}
Example: [read_file, write_file, web_search]

### Output Contract
Write result to: artifacts/sub_{agent_id}_output.md
Required fields:
  - status: success | partial | failed
  - summary: {one paragraph}
  - outputs: {list of artifact paths created}
  - blockers: {any issues encountered}

### Completion Signal
On finish (success or failure), write to artifacts/notifications/:
  Success: <task-notification type="completed" agent="{agent_id}" summary="..." />
  Failure: <task-notification type="failed" agent="{agent_id}" reason="..." />

### Budget & Constraints
Max tool calls: {N}
Do NOT: {explicit prohibitions 鈥?files not to touch, scopes not to exceed}
Do NOT: modify files outside your assigned output path
Do NOT: exceed budget without writing a blocker notification first
```

### Coordinator Monitor Loop

After spawning workers, the coordinator must monitor notifications:

```
MONITORING PROTOCOL:
  1. Poll artifacts/notifications/ every N turns (or after each tool call)
  2. For each notification:
     type="completed": read sub_{agent_id}_output.md, verify output contract
     type="failed":    read failure reason, decide: retry | skip | HITL

  3. On worker timeout (no notification within budget):
     鈫?Write: F-007 WORKER_TIMEOUT | agent={id} | budget_used={n}
     鈫?Decide: can task complete without this worker's output?
       YES: proceed with partial result, note in trajectory
       NO: HITL pause with coordinator status report

  4. DO NOT acknowledge workers in final output
  5. DO NOT copy-paste worker outputs 鈥?SYNTHESIZE

  6. After all workers complete or timeout:
     鈫?Merge: read all sub_*_output.md files
     鈫?Resolve conflicts: if workers modified overlapping resources, determine correct state
     鈫?Synthesize: produce unified output that serves the original task
```

### Execution Modes

#### Sequential (/coordinate)
```
Phase 1: [description] 鈫?output: {file} 鈫?gate: {criteria}
  鈫?verify gate passes
Phase 2: [description] 鈫?output: {file} 鈫?gate: {criteria}
  鈫?verify gate passes
...
```

#### Parallel (/orchestrate)
```
Spawn simultaneously:
  Worker A: {brief} 鈫?output: artifacts/sub_a_output.md
  Worker B: {brief} 鈫?output: artifacts/sub_b_output.md

Wait for all notifications.
Merge results.
Synthesize final output.
```

#### Ultrawork 5-Phase (/ultrawork)
Five-phase workflow with quality gates.

```
PHASE 1: PLANNING
  Actions: read context files, decompose task, define quality gates, assign workers
  Output:  artifacts/plan_{task_id}.md
  Gate:    Plan covers all sub-goals, model routing defined, budgets assigned
  Model:   reasoning-model (reasoning-heavy)

PHASE 2: RESEARCH & CONTEXT
  Actions: gather information, resolve ambiguities, validate assumptions
  Output:  artifacts/research_{task_id}.md
  Gate:    All unknowns resolved, dependencies identified, no blocking ambiguities
  Model:   fast-model (search/read heavy)

PHASE 3: EXECUTION
  Actions: spawn workers for parallel sub-goals, execute serial steps
  Output:  artifacts/sub_*_output.md + artifacts/notifications/*.xml
  Gate:    All workers completed (success or acceptable-partial), output contracts met
  Model:   per worker routing decision from Phase 1

PHASE 4: REVIEW
  Actions: review all outputs vs original task, run evaluation skill, fix issues
  Output:  artifacts/review_{task_id}.md + any corrections
  Gate:    All evaluation metrics pass (TCR 鈮?85%, TCSR 鈮?90%); no regressions
  Model:   reasoning-model (judgment-heavy)

PHASE 5: DELIVERY
  Actions: synthesize final output, write trajectory, extract memories, update CONTEXT.md
  Output:  artifacts/output_{task_id}.* + trajectory_{task_id}.md
  Gate:    Final output matches delivery criteria from mission.md
  Model:   reasoning-model (synthesis)
```

### Scratchpad (Coordinator Shared Memory)

For long coordinator sessions, use the scratchpad directory for durable cross-worker knowledge:

